# 数据存储方案（麦麦军团）

麦麦军团是单机向的收集+攻略游戏，玩家数据需要**长期保存**、**按天结算**、并且**对玩家完全透明**。本文记录存储层的选型对比、表结构设计、核心实现机制与安全边界。

---

## 一、方案对比

| 方案 | 安装部署 | 多端同步 | 数据一致性 | 本地可玩 | 成本 | 适用场景 |
| --- | --- | --- | --- | --- | --- | --- |
| A. JSON 文件存档 | 零依赖 | 无 | 弱（并发写易丢） | 是 | 零 | 单文件演示原型 |
| B. **本地 SQLite（选用）** | 零外部依赖 | 无 | 强（事务 + WAL） | 是 | 零 | 单机游戏、桌面应用 |
| C. 托管云数据库 | 需账号与凭据 | 强 | 强 | 否 | 按量计费 | 多端排行榜、联机玩法 |

**选择方案 B 的理由：**

1. **零运行时依赖**：使用 Node.js ≥ 22.5 内置的 `node:sqlite` 模块（`DatabaseSync`），`npm install` 不引入任何数据库驱动，clone 下来 `node server.mjs` 即可运行。
2. **事务 + WAL**：每日签到、打卡、攻略、建设都涉及"读状态 → 校验 → 写多条记录"，SQLite 事务保证这些步骤要么全部成功要么全部回滚，不会出现"领了奖励但没扣次数"的中间态；WAL 模式让读写在崩溃时也不损坏库。
3. **数据透明**：玩家库文件是单个 `mcm-legion.db`，可以用任意 SQLite 工具打开核对，契合挑战赛对"诚实游戏"的期待。
4. **接口隔离**：所有读写都收敛在 `src/store/LocalSqliteStore.js` 一个类里，未来若要接云端数据库，只需新增一个实现同样接口的 Store 类，游戏引擎零改动（见第六节）。

## 二、表结构设计

数据库文件：`data/mcm-legion.db`（首次启动自动创建，已加入 `.gitignore`；可用 `MCD_DB=data/test.db` 指定独立存档）。

共 9 张表，完整 SQL 见 `src/store/schema.sql`。

### 1. player — 玩家档案

单行表，记录玩家名与最后活跃日期（用于跨日检测）。

### 2. units — 军团编制

| 字段 | 说明 |
| --- | --- |
| type | `fan`（麦麦粉）/ `jun`（麦麦军）/ `general`（麦麦将军）/ `warrior`（美食战士）/ `animal`（偶遇动物） |
| key | 单位唯一标识，如 `general_320104`（将军按门店编码）、`warrior_fries` |
| name | 展示名；将军存门店名、麦麦粉存性别（`男`/`女`）、偶遇动物固定为空串 |
| count | 持有数量，`(type, key, name)` 为主键 |

按 `(type, key, name)` 聚合而不是每单位一行记录，是为了让"同一天再次打卡同一门店"这类增量操作变成一次 `count = count + 1`。

> 主键带 `name` 的代价：同一个 key 写入不同 name 会变成两行。`general` 依赖它区分不同门店的将军，`fan` 依赖它区分性别；而**偶遇动物不参与任何按 name 区分的逻辑**，却曾因历史版本把动物名写进 `name`，与新版本写入的空串行并存，导致同一只动物被渲染成两张卡片。现在的约束是：动物行的 `name` 恒为空串，写入前先清空当天动物行（`replaceAnimalUnit`），并在引擎构造与每次 `rollover()` 时做归一化（`normalizeAnimals`）自愈历史脏数据。
>
> 更隐蔽的一条：`engine.army()` 返回的 `name` 对动物而言是**展示名**（`title`，如「夜巡」），而 `attack()` 用 `type|key|name` 组工作副本、结算后又原样 `setUnitCount()` 写回，于是每攻略一次据点就会 upsert 出一行 `name=展示名` 的新行，动物免疫战损、旧的空串行不会被删——**一次攻略必然把动物复制成两只**。因此 army 详情额外提供 `storeName`（真实存储名），凡是要回写数据库的路径一律用 `storeName`，展示名只用于渲染。

### 3. stores — 打卡过的门店

记录门店编码、名称、是否已被消耗过将军（`has_general = 0` 表示该店的将军已在建设任务中消耗，之后再次打卡只发麦麦军）。

### 4. daily_log — 每日行动流水

`(date, action)` 唯一约束，`action` ∈ `checkin / clockin / encounter / orders / dispatch`。这是所有"每日一次"规则的唯一事实来源，防止通过重复请求刷奖励。

### 5. clockin_log — 打卡流水

`(date, store_code)` 唯一约束，保证"同一门店同一天只能打卡一次"；换一家门店则可以再次打卡，**每天最多 3 次**（`DAILY.clockinPerDay`）。

每日次数的判定直接 `SELECT COUNT(*) FROM clockin_log WHERE date = ?`，放在打卡流程最前面——这样纯本地就能拦下超额请求，不必先打一次 MCP 去解析门店。达到上限后前端门店列表整体置灰禁用，弹窗标题右侧实时显示"今日 x/3"。

### 6. animal_seen — 动物图鉴

偶遇过的动物 ID 集合，用于图鉴展示（动物本身只当天有效，图鉴永久记录）。

### 7. strongholds — 据点状态

| 字段 | 说明 |
| --- | --- |
| key | 据点标识，如 `cheap_0` |
| damage | 当前损毁阶段 0~5，0 = 完好无损 |
| conquered | 是否已完全损毁（攻略完成） |
| build_step | 建设进度 -1（未开启）~ 5（竣工） |
| manager_name | 开启建设时消耗的将军名（显示为"店长"） |

### 8. battle_log — 战报流水

每次攻略的阶段推进与战损明细，前端战斗日志与"最近战报"列表都读这张表。

### 9. achievements — 成就解锁记录

`key` 为主键（`src/game/achievements.js` 中的成就标识），`unlocked_at` 记录解锁时刻。用 `INSERT OR IGNORE` 写入，天然幂等——重复达成不会覆盖首次解锁时间。

## 三、核心实现机制

### 1. 跨日结算（rollover）

每个动作开头都调用引擎的 `rollover()`：比对 `player.updated_at` 与今天的日期部分，若跨天则清空 `units` 中 `type='animal'` 的行（昨天的动物离队），并把 `updated_at` 刷成当前本地时间。图鉴是另一张表（`animal_seen`），不受影响，动物离队后仍永久记录在册。

> 实现踩坑：早期版本用 `new Date().toISOString().slice(0, 10)` 取日期，这是 **UTC 时间**，在东八区傍晚之后会算出"明天"，导致动物刚领就被 rollover 清掉。现在统一用 `nowLocalStr()` 返回本地时区字符串。

### 2. 每日限制与去重

- "每日一次"类行为（签到/偶遇/派遣）先查 `daily_log` 再执行，通过后立即写回，重复请求会被拦在第二步；
- 订单奖励把已发过的订单 ID 数组序列化进 `daily_log` 的 `detail`（`{ rewarded: [orderId, ...] }`），每笔真实订单只能领一次，防止重复调用 `/api/orders` 刷战士；
- 打卡同时写 `daily_log`（计次）与 `clockin_log`（计门店）。

### 3. 随机策略（可复现 + 防刷）

随机数一律来自 `src/game/rng.js`，分两套：

- **确定性随机 `pickDaily`**（`mulberry32(seed)`，种子 = `hashSeed(日期串 + 用途 + 序号)`）：用于**订单战士**。种子含订单 ID，同一笔订单永远对应同一位战士；已发放的订单记在 `daily_log.detail`，重复领取只会补发新订单。
- **真随机 `pickRandom`**（`crypto.randomInt`）：用于**偶遇动物**与**签到麦麦粉的性别**。若偶遇按日期取种子，玩家重置进度后同一天会永远遇到同一只动物，收集玩法就废了；偶遇本身受"每日 1 次"限制，真随机不影响刷取防控。
- 攻略与建设不涉及随机。

### 4. 攻略状态续进

`attack()` 从 `damage` 当前阶段续攻（`stagesToDo = 5 - damage`），而不是从头打起；每阶段结算后若战力已低于据点防御力则中断，等待玩家补充战力。每阶段损失约 30% 战力（"就近逼近"算法，整数单位整体消耗），但麦麦将军与动物不参战、零损失。

### 5. 建设任务推进

`dispatchBuild()`：首次派遣消耗 1 名麦麦将军（记为店长，`manager_name`），之后每次派遣消耗 1 名麦麦军推进一个步骤，共 6 步，每天最多派遣 1 次。

## 四、目录与备份

```
data/
  mcm-legion.db       # SQLite 主库
  mcm-legion.db-wal   # WAL 预写日志（正常关闭后自动合并）
```

备份 = 复制 `data/` 目录；顶栏「重置」调用的 `/api/reset` 会清空全部游戏数据——包括军团编制、打卡地、图鉴（`animal_seen`）与成就，便于从零重新体验。

---

## 五、MCP 数据的边界

MCP（门店检索 / 订单列表）只作为**玩法触发器**使用：返回的门店与订单决定"能打卡哪家店、能领几位战士"，服务器不存储任何 MCP 原始响应，也不存储用户的麦当劳 Token。未配置 Token 时自动进入离线演示模式（MOCK 门店 + 确定性演示订单），玩法完全一致。

## 六、接口契约与迁云路径

`LocalSqliteStore` 对外暴露的方法即存储契约，游戏引擎（`src/game/engine.js`）只依赖这些方法：

```js
// 玩家与单位
ensurePlayer(name) / getPlayer()
listUnits() / getUnitCount(type, key, name) / addUnit(type, key, name, n)
removeUnit(type, key, name, n) / setUnitCount(type, key, name, count) / clearByType(type)
replaceAnimalUnit(key, n) / normalizeAnimals()
// 打卡地
upsertStore({ storeCode, storeName, address }) / getStore(code) / listStores()
recordClockin(storeCode, date, gotGeneral) / markGeneralConsumed(code)
// 每日流水与图鉴
getDaily(date, action) / listDaily(date) / hasAnyDaily(action) / markDaily(date, action, detail)
markAnimalSeen(key, date) / listAnimalsSeen()
// 据点与战报
ensureStrongholds(keys) / getStronghold(key) / listStrongholds() / updateStronghold(key, fields)
addBattleLog({ date, stronghold, detail }) / listBattleLogs(limit)
// 成就
listAchievements() / hasAchievement(key) / unlockAchievement(key, at)
```

> 跨日结算 `rollover()` 在游戏引擎（`src/game/engine.js`）上，它调用 `getPlayer()` + `clearByType('animal')` 并回写 `player.updated_at`；全量重置 `reset()` 同样由引擎执行（直接清表后重建 player 与 strongholds）。

要迁到云端（如 MySQL / PostgreSQL / 托管数据库）时：

1. 新建 `src/store/CloudStore.js`，实现同一组方法；
2. 在 `server.mjs` 中按环境变量切换 Store 实例；
3. `daily_log` / `clockin_log` 的唯一约束原样搬到云端表（或改用 Redis 计数器）；
4. 游戏引擎、前端、CLI 均无需改动。
